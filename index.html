CHAPTER 1 & 2 :: OVERVIEW & SCOPE

專案願景與品質目標

💡 遊戲願景與特色
發想自指令遊戲《Type help》。以黑白極簡 Terminal 風格，結合資安 CTF 輸入解謎與暴風雨山莊心理驚悚敘事（五重人格解離）。
🛡️ 技術邊界設定
純前端無後端架構。採用原生 HTML5、CSS3、ES6+ JavaScript，免除伺服器依賴、資料庫建置成本與帳號隱私外洩風險（NF-08）。
⚡ 關鍵品質指標
  • 0.1 秒回應：指令記憶體同步解析（NF-01）
  • 100% 防呆：未捕捉例外不發生（NF-02）
  • 3 秒初載：輕量無框架單頁應用（NF-07）
🎯 需求銜接（SRS 轉 SDD）
本設計文件承接 SRS-2026-001-1 的 12 項功能需求（F-01~F-12）與 10 項非功能需求（NF-01~NF-10），透過 IEEE Std 1016 設計實體屬性，將「需求規格」嚴謹轉譯為「五大模組程式結構與資料模型」。
CHAPTER 3.1 :: ARCHITECTURAL DESIGN

系統架構：單頁事件驅動五模組

依照 IEEE 1016 分解視圖（Decomposition View），系統劃分為職責明確、相互解耦的五大核心模組：
模組名稱 實作檔案 核心責任 (Responsibilities) 負責組員
指令解析 (Parser) parser.js 輸入清洗、大小寫歸一化、正則語法分析、多人指令排序校驗 王文伶
狀態管理 (State) state.js 章節地點管理、五角色暱稱、14 幕進度切換、LocalStorage 存讀檔 王文伶
UI 渲染 (UI Controller) ui.js 打字機逐字印出、Enter/Space 跳過動畫、終端游標閃爍、歷史視窗 余苡萱
錯誤處理 (Error Handler) errorHandler.js 截獲無效指令、回傳驚悚風格錯誤提示、永不中斷玩家操作 王文伶 / 杜汯溱
音效控制 (Audio) audio.js Web Audio API 播放打字音、關鍵提示音（knock.mp3）、防靜音阻擋 杜汯溱
CHAPTER 3.1 & 3.2 :: DEPENDENCY & SEQUENCE

相依視圖：單次指令處理資料流

🔄 事件驅動處理序列 (Event Lifecycle)
  1. 玩家輸入：鍵入字串並觸發 Enter 事件。
  2. 介面移交：ui.js 鎖定輸入框，將 raw string 送入 parser.js。
  3. 語法剖析：parser.js 驗證通過回傳 {type, args}；失敗則轉向 errorHandler.js。
  4. 狀態變更：state.js 依指令更新 GameState，並自動觸發 autosave() 寫入 LocalStorage。
  5. 輸出渲染：ui.js 執行打字機動畫，並呼叫 audio.js 伴隨按鍵音效；完成後重新釋放輸入框。

元件演算法 (一)：指令解析模組 (parser.js)

📝 支援指令語法規範
指令語法 類型說明 對應需求
simple 取得當前階段關鍵提示 F-02
list 列出已解鎖物件與章節 F-03
inspect [物件] 調查房間/物品細節 F-04
05_HO_05 / 05_HO_123 複合劇情推進 (章節_地點_人物) F-05
name [P1~P5] [新名稱] 角色重新命名 (保留原始代號) F-06
history / log 開啟對話回顧歷史面板 F-07
save [N] / load [N] 槽位存讀檔操作 F-08
⚡ 指令比對核心邏輯 (虛擬碼)
function parseCommand(raw):
  s = raw.trim()
  if s == "": return {error: "EMPTY"}
  lower = s.toLowerCase()

  // 劇情指令：正規表達式匹配 (如 05_ho_123)
  if lower.matches(/^(\d{2})_([a-z]{2})_(\d+)$/):
    (ch, loc, who) = captures
    // 多人代號必須由小到大嚴格遞增排序
    if isMulti(who) and !isAscending(who):
      return {error: "ORDER"}
    return {type: "STORY", args: [ch, loc, who]}

  tokens = s.split(/\s+/)
  head = tokens[0].toLowerCase()
  // 參數長度與格式驗證分派...
  return dispatchToken(head, tokens.slice(1))
CHAPTER 5.2 :: STATE DYNAMICS

元件演算法 (二)：遊戲狀態管理 (state.js)

🎭 14 幕推進與五重人格管理
系統控管主角 Mara (P1) 與其他四位分支人格（Lumi, Ash, Eve, Iris）的真名解鎖狀態；指令 name P1 新名 僅更新顯示暱稱，底層固定識別碼不變（F-06-04）。
🧩 關鍵解謎：符文連線序列演算法
第 13~14 幕解謎要求玩家按嚴格順序連線房間節點：
301 (天台) ➔ 204 (命案現場) ➔ 205 (密室) ➔ 103 (診斷室)

若輸入錯誤順序立即清空陣列並重置；全數匹配成功時，觸發第 14 幕輪迴大結局 triggerAct14()（敲門聲 Knock Knock）。
🖥️ 狀態變更分派 (State Dispatch)
function updateState(cmd):
  switch cmd.type:
    "STORY":
      node = story.find(act, loc, who)
      if !preconditionMet(node): 
        return err("NO_STORY")
      apply(node.effects)
      appendHistory(node.text)
      advanceAct()
    "INSPECT":
      return inspectObject(cmd.args[0])
    "NAME":
      return renameEntity(cmd.args)
    "SAVE" / "LOAD":
      return executeStorage(cmd)
  
  autosave() // 每次成功變更即自動存檔
CHAPTER 4 :: DATA DESIGN & STORAGE

資料設計與 LocalStorage 儲存模型

📦 LocalStorage Key 規範與 JSON 結構
採用 Web LocalStorage API，使用結構化 Key 進行多槽位管理：
  • k33p_slot_1 ~ k33p_slot_5：指定存檔槽位
  • k33p_auto：每次指令成功執行後之自動存檔
  • k33p_settings：終端風格與音效設定
{
  "version": 1,
  "chapter": "05",
  "location": "HO",
  "playerName": "User",
  "names": { "P1": "Mara", "P5": "Iris" },
  "unlockedRealName": false,
  "unlocked": { "objects": [], "chapters": ["01"] },
  "runeConnections": ["301", "204"],
  "savedAt": "2026-11-08T12:00:00Z"
}
🛡️ 存檔可靠性防護 (NF-06)
  • Schema 結構驗證：讀檔時利用 validSchema(data) 嚴格驗證版本與必要欄位型別。
  • 損毀保護機制：若遭遇惡意竄改或 JSON 解析錯誤，系統拋出 LOAD_FAIL，嚴禁覆蓋當前記憶體狀態。
  • 容量與權限異常捕獲：存檔使用 try...catch 包覆，當 LocalStorage 空間不足或被無痕模式停用時，優雅提示錯誤（SAVE_FAIL）。
